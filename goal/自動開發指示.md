# 自動開發指示（`/goal` 用，不限 AI 工具）

> 本檔是 `/goal` 執行時的完整工作指示。**執行中不得修改本檔與 `verify-local.sh`**；需要修改時由人類停止 goal 後修改。
> 第 0～6 節是單一 agent（模式 A）的做法；多個 agent 同時工作（平行開發、實作＋審查）時，另外套用第 7 節的差異。
> 本檔不綁定任何 AI 工具；各工具怎麼啟動（從哪個資料夾、怎麼讓它能寫入三個 repo、怎麼輸入完成條件）見 `goal/runners/`。
> 這是一份範本：以「依 `11-開發計畫.md` 第二節新增一個業務模組」為例。換成別的開發目標時，人類只需要改第 1 節的範圍與第 5 節的驗收項目，並同步修改 `verify-local.sh` 的 `REQ_TESTS`、`REQ_E2E`。

---

## 0. 位置

三個 repo 放在同一層資料夾：

| 項目 | 路徑 |
|---|---|
| 文件（本檔、驗收腳本、進度檔） | `multitenant-starter-docs/`、`multitenant-starter-docs/goal/` |
| 後端 | `multitenant-starter-backend/` |
| 前端 | `multitenant-starter-frontend/` |

**每一輪開始時**，先讀 `goal/PROGRESS.md`（不存在就建立），確認目前做到哪裡、下一步是什麼。對話被自動壓縮後，以 `PROGRESS.md` 與 git 歷史為準，不憑記憶。

**第一輪**，依序讀完：`AGENTS.md`、`00-文件規範.md`、`03-決策紀錄.md`、`02-需求書.md`、`05-資料庫設計.md`、`13-系統架構設計.md`、`11-開發計畫.md`、本檔，以及後端、前端 repo 根目錄的 `AGENTS.md`。

## 1. 範圍

（範例）依 `11-開發計畫.md` 第二節的檢查清單，新增 `02-需求書.md` 中已確認的新業務模組，以 `verify-local.sh` 全部通過為完成。

**不做**：`02-需求書.md` 第四節排除的範圍、`11-開發計畫.md` 第三節「之後可以做的方向」。

## 2. 開始前檢查（不通過就停止）

1. 新模組的需求已寫進 `02-需求書.md`，取捨已寫進 `03-決策紀錄.md`，`13-系統架構設計.md` 已有 API 清單與業務規則，且沒有「待確認 #」「建議，待確認」標記
2. 後端、前端兩個 repo 都在 `main`、`git status` 乾淨
3. `docker info`、`java -version`（21）、`pnpm -v`（10）都能正常執行

任一項不通過：依第 3-2 節寫入 `BLOCKED.md` 並停止。

---

## 3. 自主決定與停止規則

### 3-1 可以自行決定（決定後記錄）
`13-系統架構設計.md` 沒有寫到的**小型實作細節**（元件拆法、變數命名、錯誤訊息文字）：自行決定，並在 13 末尾的「實作中的決定」小節（沒有就新增）逐條記錄「決定了什麼、為什麼」，供人類事後審核。

### 3-2 必須停止（寫入 `BLOCKED.md` 後停止）
- 發現兩份文件互相矛盾，或實作會推翻 `03-決策紀錄.md` 的任何決策、超出 `02-需求書.md` 範圍
- 需要新增 13 沒有列出的第三方套件
- 同一個驗收項目連續修了 5 輪仍然失敗，而且判斷問題不在程式本身（例如環境、網路）

`BLOCKED.md` 寫：卡住的是什麼、相關文件與條目的原文、可行的做法與各自優缺點、你的建議。寫完後，回覆的第一行輸出 `BLOCKED: 見 goal/BLOCKED.md`，不再繼續任何工作。

### 3-3 絕對禁止
- `git push`（模式 A 一律禁止；平行或審查模式依第 7 節）、修改 git remote、改寫已存在的 commit 歷史
- 把密碼、金鑰寫死在程式碼（本地測試用的值只能放在 `.env.*`、測試設定、`scripts/dev-env.sh` 或 `verify-local.sh` 已有的環境變數）
- 為了通過驗收而跳過、刪除、弱化測試，或關閉 RLS、繞過權限檢查
- 修改本檔、`verify-local.sh`

## 4. 做法

1. 從 `main` 開分支 `feat/<英文簡稱>`（兩個 repo 都有改動就兩邊都開）
2. 依 `13-系統架構設計.md` 實作，順序：
   - 後端：Flyway migration（含 RLS policy）→ Entity → Repository → Service → Controller → 測試
   - 前端：`server/<編號>-<功能>/` 的 Server Action 與型別 → 頁面與元件 → 手機版 → E2E 測試
3. 執行 `bash goal/verify-local.sh`，修到通過
4. 同步更新文件（依 `00-文件規範.md` 第三節）：`05-資料庫設計.md`、`11-開發計畫.md`（完成的項目改成 `[x]`）、`09-變更日誌.md`、`12-使用者操作說明.md`、`13-系統架構設計.md`（實作中的決定）、`01-README.md`（啟動方式或環境變數有變時）
5. commit（Conventional Commits 格式，例如 `feat(invoice): 發票新增與作廢`），切回 `main` 以 `git merge --no-ff` 合併，刪除分支
6. 更新 `PROGRESS.md`：完成了什麼、合併的 commit、`verify-local.sh` 最後 10 行輸出

程式規範遵守 `AGENTS.md` 第 3、4 節。

## 5. 驗收項目（`verify-local.sh` 依賴這些名稱）

### 5-1 本地環境的固定約定
- 本機 PostgreSQL、Redis 以後端 `docker/docker-compose-local.yml` 啟動；執行用帳號 `starter_app`（密碼 `starter_app_local`，非 superuser、非資料表擁有者），建表帳號 `root`／`starter_owner_local`
- 預設總管理員 `admin`／`admin`，第一次登入就要改密碼

### 5-2 後端必須存在且通過的測試類別

| 測試類別 | 必須證明的事 |
|---|---|
| `TenantIsolationIT` | 兩個租戶各自的帳號，透過每一支業務 API 都拿不到對方的資料（**新增資料表與 API 時一定要擴充**） |
| `RlsFailClosedIT` | 沒有設定目前租戶的交易查不到任何資料；總管理員新增、修改、刪除業務資料表都被資料庫拒絕；手寫 SQL 一樣被 RLS 限制 |
| `AccountManagementIT`、`LoginLockoutIT`、`PasswordPolicyTest` | 帳號管理、強制改密碼、登入鎖定、密碼規則 |
| `AuditLogIT`、`AuditServiceChangesTest` | 每種操作都留下紀錄；租戶帳號讀不到操作紀錄 |
| `CustomerOrderApiIT`、`SalesOrderEntityTest` | 範例業務模組的規則 |
| （新模組的測試） | 新模組的業務規則；加到 `verify-local.sh` 的 `REQ_TESTS` |

### 5-3 E2E 測試（Playwright）
- 位置 `multitenant-starter-frontend/apps/starter/e2e/`；資料庫是每次驗收重建的空資料庫，測試依序執行、自行建立所需資料
- 每個測試標題以編號開頭：`E2E-01`～`E2E-03`、`E2E-09`（帳號與租戶）、`E2E-04`～`E2E-06`（範例業務模組）、`E2E-12`（操作紀錄）；新模組的 E2E 從 `E2E-13` 開始編號，並加到 `verify-local.sh` 的 `REQ_E2E`

---

## 6. 完成

`bash goal/verify-local.sh` 退出碼為 0、最後一行為 `ALL CHECKS PASSED`。把該次完整輸出貼在最後的回覆中，並在 `PROGRESS.md` 寫上完成時間與需要人類審核的項目（13 的實作中的決定）。

## 7. 平行或審查模式的差異（模式 B、C）

依 `14-多代理協作規範.md` 與 `tasks/README.md` 執行。以下逐條說明與第 0～6 節不同的地方，沒有列出的照原本規定：

| 原本的規定 | 平行或審查模式 |
|---|---|
| 第 0 節：每一輪先讀 `goal/PROGRESS.md` | 改讀自己的任務卡（以及 `tasks/<任務編號>-審查.md`，如果有），**並檢查主分支有沒有 `STOP.md`**（`14` 第 8 節）；進度寫在任務卡「進度」 |
| 第 1 節：範圍 | 以任務卡「範圍」「可以修改的檔案與目錄」「不做」為準 |
| 第 2 節第 2 點：兩個 repo 都在 `main` | 三個 repo 都在任務卡指定的任務分支，而且在自己的工作目錄（`tasks/README.md` 第 3 節） |
| 第 3-1 節：實作中的決定寫進 13 | 模式 B 寫在任務卡「實作中的決定」，由整合者移到 13 |
| 第 3-2 節：寫入 `BLOCKED.md` | 寫在任務卡「阻礙」、狀態改為「阻礙」，回覆第一行輸出 `BLOCKED: 見 tasks/<任務卡檔名>` |
| 第 3-3 節：禁止 `git push` | 只能推送自己的分支；推送主分支、force push、修改 remote 仍然禁止（`14` 第 10 節） |
| 第 4 節第 1 點：分支 `feat/<英文簡稱>` | 使用任務卡指定的分支（`feat/<任務編號>-<英文簡稱>`） |
| 第 4 節第 3 點：`bash goal/verify-local.sh` | 加上任務卡的槽位與分支：`AGENT_SLOT=<槽位> VERIFY_BRANCH=<任務分支> BACKEND=… FRONTEND=… bash goal/verify-local.sh`（`tasks/README.md` 第 4 節） |
| 第 4 節第 4 點：同步更新文件 | 模式 B 不改 `02`、`03`、`09`、13 的「實作中的決定」、11 的完成勾選，改寫在任務卡（`14` 第 4 節）；資料庫遷移版本與 E2E 編號只能使用任務卡「預先分配」的號碼 |
| 第 4 節第 5 點：切回 `main` 合併 | **不合併**。commit 時訊息結尾加上 `Agent:`、`Task:` 兩行，狀態改為「待審查」或「待整合」（只有模式 C 時審查通過後改為「待人類審查」） |
| 第 6 節：完成條件 | 實作者用 `goal/goal-condition-task.txt` |
